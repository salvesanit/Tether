# Synthetic data — how Aster and its answer key were built

Synthetic = written by the team, marked `(synthetic)`, describing nobody. Aster — a campus club events app, one student lead on two weeks' notice — is invented end to end.

## Method

1. **The answer key was written first** — `data/demo_project/answer_key.json`: 61 facts across the seven claim types (16 decisions ≥ the 16 required), 20 fakes (7 invented, 7 altered, 6 with the wrong locator), 6 contradictions, 6 gaps (six of the twelve successor-needs subjects with no evidence anywhere: accounts & credentials, third-party services & vendors, data & backups, contacts, deadlines, access), rejected options for ≥3 decisions, one restricted source, one mixed-label claim, one note carrying a prompt injection, two excluded chat channels each holding a honeytoken, and several obviously fake secrets plus a fake phone number and personal email.
2. **Sources were then written to satisfy the key** — `data/demo_project/`: `repo.bundle` (~60 commits; see `make seed`), `issues.json` / `prs.json` (GitHub REST shapes with comments), 15 Markdown notes, `chat.json`, `manifest.json` (labels + the two excluded channels). Every planted quote exists at its locator — prove it with `python3 -m pytest backend/tests/test_key1_answer_key.py -q` (KEY-1) and `backend/tests/test_rd.py -q` (RD-1).
3. **Replay fixtures are honest** — `fixtures/llm/extract-claims-v3.<hash>.json`, one per unique chunk, provenance `handwritten-reference` (never called model output), derived from the planted key, regenerated by `make record` (`scripts/record_fixtures.py`). Byte-identical chunks (the same sentence in a note and in chat) share one fixture — positions are unioned deterministically.
4. **Fake-claims keep honeytokens out** — no fixture carries a honeytoken, so a dropped claim can never carry one into the dropped list.
5. **COUNTING.** Reports count what happened: kept/dropped/conflicts/gaps. Never a loss rate, never a percent. Replay mode means the score shows the checks and the plumbing work, not that a model is good.

## What is which

| Thing | Where | Kind |
|---|---|---|
| Planted facts & fakes | `answer_key.json` | planted, synthetic |
| Replay responses | `fixtures/llm/` (165 spans → 164 files) | handwritten-reference |
| People (Aarav, Sanit, Diya, Krushna) | users table seeded by `make seed` | invented, (synthetic) |
| Secrets/phone/email | inside `repo.bundle`, notes and chat | obviously fake formats (AWS-documentation-style example key etc.) |
| Honeytokens | `#hr-leave`, `#private-aarav` only | invented phrases, marked (synthetic) |
| Notes/chat/repo content | all files under `data/demo_project/` | authored for the demo, fictional |

Never presented as real company data; never reused as training or evaluation data outside this project.

## Redaction and leakage tests

SEC-1 (honeytokens): neither token reaches the database, logs, exports or API. SEC-2 (secrets/PII): planted secrets and the phone/email appear only as `[REDACTED:type]`; the scanner is the built-in gitleaks-style regex set in `backend/app/pipeline/clean.py`, **not** the gitleaks binary. SEC-3 (injection): the planted note is quarantined and moves no gate. These are the claims that are tested; nothing else is claimed.
